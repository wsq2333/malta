# Benchmark 方法与比较规则

状态：方法设计，尚未实现。目标是让每一个性能数字都附带条件、重复实验和可追溯证据。

## 1. 首批负载

| 场景 | 主要观测 | 必须固定的条件 |
| --- | --- | --- |
| 大块顺序读 | 持续吞吐、尾延迟 | 数据是否已准备、缓存状态、文件布局与块大小 |
| 大块顺序写 | 吞吐、尾延迟 | 文件扩展/覆盖、同步与持久化语义 |
| 小块随机读 | IOPS、尾延迟 | 工作集、随机种子、读热点、direct/buffered |
| 小块随机写 | IOPS、尾延迟 | 预分配、覆盖方式、数据生成方式和同步策略 |
| 混合读写 | 读写各自吞吐、IOPS、尾延迟 | 读写比例、工作集和并发模型 |

首版由 fio 执行。fio 的 JSON/JSON+ 提供结构化输出；JSON+ 还包含完成延迟桶，用于保留和重建相应分布。解析器需按受支持工具版本验证字段与单位。[fio 文档](https://fio.readthedocs.io/en/latest/fio_doc.html)

后续使用 IOR 评估并行 I/O，使用 mdtest 评估元数据操作；两者依赖 MPI 进行同步，因此在多客户端阶段增加对应运行环境和版本记录。[IOR 文档](https://ior.readthedocs.io/en/latest/)

## 2. 单次实验流程

1. 校验目标目录、空间、工具版本、I/O 引擎及选项支持情况。
2. 采集客户端和可获取的服务端环境；缺失信息标记 unknown。
3. 准备数据，记录文件数、大小、内容生成方式、准备结果。
4. 按定义执行预热和缓存准备，记录每一步是否成功。
5. 执行固定测量窗口，采集工具输出及可选资源时序。
6. 检查退出状态、错误、实际时长和输出完整性。
7. 保存原始证据与规范化结果，再进入下一次重复或参数点。

准备、预热、测量、清理分开计时。不能用一次未完成的读取或仅写入内存缓存的速度代表稳定存储性能。

## 3. 缓存与写入语义

缓存状态至少区分 warm、cold-requested、cold-verified、unknown，并记录证据。客户端、文件系统服务端和底层存储可能各有缓存；direct I/O 不等于端到端冷缓存，数据集大于客户端内存也不能证明服务器缓存未命中。

不自动执行机器级清缓存。若测试方案明确包含缓存操作，应记录具体层次、方法和执行结果；无法验证时不标记 cold-verified。cold 与 warm 结果分别展示。

记录 buffered/direct I/O、同步/异步引擎、fsync/fdatasync 策略和文件系统提供的持久化保证。普通写调用完成、客户端 flush 完成、服务端持久化不是同一个语义，不能混为一个写性能指标。

## 4. 重复实验和统计

每个参数点默认规划至少 3 次独立重复。展示成功数/计划数、各次值、中位数、最小值、最大值和波动说明；可增加 IQR/MAD。三次重复只是起点，不能据此保证统计显著性。

缺失、失败、取消和中断保留状态，不插值为零。未完成计划次数时可展示已完成结果，但标记不完整，不自动晋升为基线。离群点保留并附注，不能静默删除。

每次 Trial 的 P99 与“多次 Trial 的 P99 中位数”是不同统计量，必须分别命名。只有单位、延迟类型、桶定义和采集条件兼容的直方图才能按计数合并并重新估计分位数；仅有分位数时不生成伪造的全局 P99。

内部规范使用 bytes、seconds、bytes/second、operations/second 和 latency nanoseconds；界面再转换为 MiB/s、ms 等。读取、写入、同步操作分别保留，`slat`、`clat`、`lat` 不混用。规范化值必须保留源字段与转换方式。

## 5. 可比性与回退

| 维度 | 版本对比要求 |
| --- | --- |
| 文件系统版本、测试日期 | 允许变化，属于对比目标 |
| 客户端与服务端硬件、网络、节点数 | 原则上固定，变化须明确作为实验变量 |
| 工作负载、数据集、文件布局、工具版本 | 固定或明确说明兼容性依据 |
| 缓存、挂载参数、压缩、去重、副本与持久化策略 | 固定；影响语义的变化不能作为直接回退结论 |
| 并发扫描范围、约束和重复策略 | 匹配；覆盖范围不同需标记，限制对峰值的直接比较 |

比较返回三种状态：comparable、qualified（有已知差异或缺失条件）、incompatible（指标语义或核心条件冲突），同时返回逐字段原因。信息未知不等于相同。用户可将配置变化指定为研究变量，但报告应标为配置实验，不能归因于版本。

变化率定义为 `(candidate - baseline) / baseline × 100%`；吞吐与 IOPS 通常越高越好，延迟和错误率通常越低越好。基线为零或指标缺失时不计算百分比，只展示绝对值和原因。百分比与百分点必须区分。

回退候选需同时考虑预先设定的容忍阈值、重复实验波动和可比性。MVP 展示差异和候选标记，不宣称因果关系或统计显著性。日期趋势只连接满足指定条件的结果，不能把不同负载的每日最大值连接成版本趋势。

## 6. 性能上限与并发扫描

固定其他条件，分别扫描 `numjobs` 与 `iodepth`，记录请求值和工具报告的实际深度。不同 I/O 引擎的队列行为不同，`numjobs × iodepth` 仅是配置层面的量，不能直接当作实际在途 I/O 数。

每个点完成预热、固定窗口测量和独立重复。运行顺序、冷却间隔和集群恢复条件写入定义；必要时交错测试版本以减小时间漂移。

提供两种明确区分的结果：

- **观测峰值**：本次扫描范围内，各点重复实验中位数的最大吞吐或 IOPS，并附带对应延迟、条件和波动。
- **约束内最佳点**：在指定 P99、错误率和完整性规则下通过的点中选取最高性能。默认要求该点所有计划重复成功且逐次满足约束。

若最高点在扫描边界、曲线仍在增长或未达到预定义稳定性标准，只报告“当前范围的最佳观测值，尚未确认饱和”。未配置约束时不能声称满足某个 SLO；没有可行点时返回无可行结果。

## 7. 多客户端与资源观测（后续）

多客户端执行需要协调开始时间、记录时钟偏差，并使用明确的公共测量窗口。缺少对齐时序或窗口不一致时，不将各客户端平均吞吐相加当作精确集群吞吐；客户端缺失或失败时标记结果不完整。

聚合吞吐按公共窗口内完成的总字节数除以窗口时长计算。客户端分位数不能平均成集群分位数。跨客户端直方图只有在覆盖相同测量区间并满足兼容条件时才合并。

资源观测可接入客户端 CPU、内存、网络及服务端指标；采样频率、来源和时间偏差都随结果记录。吞吐平台期只能作为瓶颈线索，还需区分客户端 CPU、网络、元数据服务和存储后端限制。采集和可视化负载的影响应通过对照测试评估。
