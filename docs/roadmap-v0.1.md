# Malta v0.1 代码实现路线图

状态：S0–S5 已完成代码与功能验证；S6–S7 正在实现。具体范围与验证见 [实现记录](implementation.md)。本文将 README 的 M0–M2 展开为可逐步验收的代码交付，既有技术选型维持 Go + TypeScript/React。

## 1. 第一版交付目标

工程师或 Agent 能选择一个版本、环境快照与负载，通过 CLI 发起本地或 Kubernetes 单 Pod 性能测试，跟踪或取消任务，保存结果，并在白底浅绿的 UI 中与基线比较。

一次完整交付演示应包含：

1. 注册两个文件系统版本与一个硬件环境快照。
2. 对每个版本执行相同的数据负载，保留计划内重复实验。
3. 导入与版本、环境及操作语义绑定的元数据结果。
4. 将第一批运行显式设为基线，与第二批比较。
5. 在 UI 查看指标、波动、配置差异及原始证据。
6. 用 Agent skill 完成相同流程，并演示查询、等待超时与取消。
7. 在 Kubernetes 挂载已有 PVC 执行一次测试，Pod 清理后仍可访问结果。

## 2. v0.1 范围

| 部分 | 必须交付 | 后续扩展 |
| --- | --- | --- |
| 数据 I/O | fio；顺序读写、随机读写、混合读写；文件大小与块大小独立；参数矩阵与重复 | 其他访问协议、IOR、多客户端同步 |
| 元数据 | 统一结果格式、一个经真实 fixture 验证的工具结果导入器、操作级基线与 UI | 自动执行完整元数据套件；rename/readdir 等按工具能力扩展 |
| 环境与版本 | 云厂商/实例类型、物理机型号、客户端/服务端拓扑、不可变快照、版本与构建身份 | 自动发现完整集群拓扑 |
| CLI | plan、exec、run 生命周期、结果导入导出、环境与版本登记/查询、基线与对比 | 插件分发、复杂工作流调度 |
| 服务 | 单实例 API、SQLite、artifact、本地与 Kubernetes 执行后端 | 服务高可用、多租户、分布式队列 |
| UI | 基线、版本、硬件环境、运行列表/详情、基础对比与趋势 | 多客户端资源联动、复杂分析工作台 |
| Agent | 可安装测试管理 skill、JSON 契约、证据可追溯的比较摘要 | 专用分析 skill、自动瓶颈归因、实验优化 |
| Kubernetes | 单 Job / 单客户端、已有 PVC、独立结果存储、取消与恢复 | MPI、多 Pod 协调、不同后端自动部署 |

元数据基线在第一版可用，但元数据原生执行器属于后续工作，当前以已验证的结果导入建立闭环。支持哪些源工具和版本必须在 S0 固定，不能把任意文本导入都宣称为支持。

## 3. 开发顺序与依赖

```mermaid
flowchart LR
    S0[S0 工程与契约] --> S1[S1 前台 fio 执行]
    S1 --> S2[S2 存储与基线比较]
    S2 --> S3[S3 托管运行与 API]
    S3 --> S4[S4 Web UI]
    S4 --> S5[S5 Kubernetes]
    S5 --> S6[S6 Agent skill 验收]
    S6 --> S7[S7 发布验收]
```

每阶段提交可运行、可验证的代码。S3 同时产生本地测试 skill 初稿，S6 在 Kubernetes 能力稳定后完成全链路验收。UI 的静态组件可以提前制作，但页面完成以真实 API 数据流为准。

### S0：工程骨架与数据契约

**实现：**

- 建立 Go module、CLI 入口、前端工程与基础构建/CI；固定依赖版本。
- 定义 TestDefinition、ExecutionPlan、EnvironmentSnapshot、Version、Run、Attempt、Trial、Artifact、Baseline、Comparison。
- 固定 schema 版本、单位、缺失值、错误分类、状态机、JSON envelope 和退出码。
- 定义 OpenAPI，覆盖运行管理、环境/版本登记查询、结果导入、基线与比较。
- 选择首批支持的 fio 与元数据结果源版本，收集脱敏真实 fixture。
- 准备小规模 smoke 负载和实验室性能负载；在模板中明确两者用途。

**主要目录：** `cmd/malta/`、`internal/domain/`、`internal/cli/`、`api/`、`schemas/`、`benchmarks/`、`testdata/`、`web/`。

**验收：** 项目可构建；示例计划和结果通过 schema 校验；非法单位、缺失必要字段和未知重大版本返回明确错误；CLI 帮助与结构化错误可用。

### S1：本地前台执行与结果包

**实现：**

- `malta plan` 校验定义和目标，生成展开后的计划与哈希，不执行 I/O。
- `malta exec` 在当前 Linux 测试节点执行计划，完成准备、预热、测量与结果收集。
- fio 适配器负责参数生成、版本/能力检查、输出解析；采用结构化参数启动子进程。
- 支持五类数据负载、文件大小/块大小、进程数/队列深度扫描及独立重复。
- 结果包保存原始输出、规范化指标、命令、工具版本与环境；混合负载读写分开。
- 实现超时和进程组取消；每次 attempt 使用受约束的独立目录，记录创建的文件。

**主要目录：** `internal/runner/`、`internal/engine/fio/`、`internal/artifact/`、`benchmarks/data/`。

**验收：** 专用 Linux 测试目录完成顺序读写、随机读写、混合负载；准备时间未混入测量；取消后没有遗留压测进程；失败保存日志；单位、IOPS 和延迟解析与 fixture 对齐。

**阶段产出：** 第一个可实际运行的 Malta CLI，可离线输出结果包。

### S2：持久化、环境管理与基线比较

**实现：**

- SQLite migrations、结果索引和不可变 artifact；导入时校验哈希、路径与 schema。
- `result import/export`、`environment register/list/show`、`version register/list/show`。
- 环境登记生成新快照，版本关联明确的 release/commit/build，缺少的自动探测信息标为 unknown。
- `baseline list/set`、`compare`：显式选择基线，检查可比性，计算差异与重复实验摘要。
- 实现基本元数据结果导入，至少覆盖源工具实际支持的文件创建、stat 和删除操作。
- 历史查询按环境、版本、负载和日期检索；保存比较规则版本与证据引用。

**主要目录：** `internal/store/`、`internal/compare/`、`internal/engine/metadata/`、`environments/`。

**验收：** 同一结果重复导入不重复计数；同 ID 不同内容报冲突；相同环境下的版本差异可比较；硬件/缓存/负载差异可见；缺失值、零基线与失败重复得到正确处理；数据与元数据结果均可建立基线。

**阶段产出：** 两批真实结果可通过 CLI 完成对照，并可追溯到原始文件。

### S3：托管任务、API 与自动化契约

**实现：**

- `malta serve` 提供单实例 API 与运行管理，local executor 在服务节点拥有运行生命周期。
- `run start/list/get/logs/wait/cancel`，提交先登记 Run/request-id，再执行。
- 实现 resource-group 串行协调、Run/Attempt 状态、结果持久化状态和服务恢复。
- 同一 request-id/计划返回同一逻辑 Run；客户端断线或 wait 超时不重新发起任务。
- `--format json`、`--non-interactive`、版本化输出与稳定退出码；流式日志采用明确的 NDJSON 契约。
- 环境配置定义允许的目标目录、执行后端与资源预算，服务端重新验证计划。
- 默认 loopback；提供服务间/远程 CLI 所需的显式认证配置，凭证不进入结果包。对外发布部署另配置传输保护。
- 按已实现的命令编写测试管理 skill 初稿，先完成 local 路径。

**主要目录：** `internal/api/`、`internal/executor/local/`、`internal/cli/`、`skills/malta-benchmark/`。

**验收：** CLI 与 API 使用同一业务规则；重复提交、断线重连、等待超时、取消和服务重启有可验证状态；恢复时不会盲目重跑写入测试或误杀无关进程；JSON stdout 不混入日志。

**阶段产出：** Agent 能可靠地管理本地任务，而不必保持同一个终端会话。

### S4：接入真实结果的 Web UI

**实现：**

- 将已确认草图转为 React 页面，固定纯白底、浅绿/薄荷绿点缀与清晰表格层级。
- 性能基线页：数据/元数据切换、文件大小与块大小、读写类型、环境与版本筛选。
- 版本与硬件环境页：登记/查看身份和快照，关联测试覆盖与基线入口。
- 运行页：人工/Agent 来源、local/Kubernetes 后端、状态、计划、错误和证据下载。
- 比较与趋势：展示服务端可比性、重复实验波动、指标差异、同条件日期趋势和并发曲线。
- 覆盖加载、空结果、失败、未采集、不可比等状态；筛选条件进入 URL，方便复现视图。

**主要目录：** `web/src/`、`web/embed.go`、`tests/e2e/`。

**验收：** 两批 S2/S3 真实结果可在页面对比；图表值与 API 一致；环境切换不串用其他快照的基线；缺失元数据延迟不显示成 0；窄屏表格可访问。

**阶段产出：** 可浏览的性能对照平台，页面使用实际数据库结果。

### S5：容器与 Kubernetes 单 Pod 执行

**实现：**

- server/runner Dockerfile，固定工具版本与镜像 digest，处理终止信号。
- kubernetes executor 提交 Job，支持查询、日志、等待、取消和 Attempt 追踪。
- `deploy/kubernetes/base/`、`jobs/`、`overlays/` 提供可验证模板与明确参数。
- PVC 挂载到 `/bench`，计划只读挂载到 `/etc/malta`，`/results` 使用独立持久存储。
- 第一版固定一种可验证的结果回传方式：例如专用结果 PVC 由 Runner 与服务按已验证访问模式读取；环境不满足该条件时明确报错。对象存储上传作为后续扩展。
- 验证 PVC 访问模式、节点拓扑、权限、资源预算和实际环境快照；提交身份与执行身份分开。
- Job/Pod UID、重启、退出码和结果导入状态写入运行记录；确认结果保存后再清理 Job。

**主要目录：** `internal/executor/kubernetes/`、`build/docker/`、`deploy/kubernetes/`、`tests/integration/`。

**验收：** 在准备好的测试集群挂载实际被测文件系统完成最小测试；取消能够停止负载；Pod 被终止、节点不可用或结果持久化失败均可追溯；重复启动不覆盖原始证据；Pod 清理后结果仍可查询。

**阶段产出：** `run start --executor kubernetes` 可完成单客户端集群内测试。

### S6：Agent skill 完整交付

**实现：**

- 完成 `skills/malta-benchmark/SKILL.md`，声明 CLI/schema 兼容版本和必需输入。
- 提供 local 与 Kubernetes 的计划、执行、监控、取消和对比范例。
- 约定运行恢复：保留 run_id/request-id，先查询状态，避免因会话中断重复压测。
- Agent 输出比较摘要时引用运行、指标、环境与 artifact；事实与假设分开。
- 补充参数缺失、超预算、结果不可比、部分失败等处理路径。

**验收：** 外部 Agent 仅按发布 skill 和 CLI 帮助，即可完成一次小规模测试与对比；无需修改代码或读取内部数据库；会话中断后能够接续已有 Run；不会将 wait 超时当作测试失败重跑。

**阶段产出：** 第一版可用的 Agent 测试管理能力。专用的自动诊断 skill 继续按后续路线推进。

### S7：发布候选与最终验收

**实现：**

- 发布二进制、前端内嵌资源、镜像与 manifest，补齐安装、配置和升级说明。
- 提供 smoke 示例、环境模板、兼容版本表与已知限制；实验室性能模板独立标注资源需求。
- 固定支持的操作系统/架构、fio/元数据工具版本，以及实测 Kubernetes/CSI 组合。
- 确定许可证，检查构建可复现性和制品校验和。
- 用以下验收清单确认 v0.1；性能验收在固定实验室环境完成。

**阶段产出：** 一个可以从干净环境安装、复现实验、查看对照的 v0.1 release candidate。

## 4. 第一版完成标准

- [ ] 干净 Linux 环境可按文档安装并启动。
- [ ] 五类数据 I/O 负载可执行；文件大小与块大小独立记录。
- [ ] 元数据结果可导入并按操作、版本和环境建立基线。
- [ ] 测试定义、工具版本、配置快照、原始输出与哈希可查。
- [ ] 云环境和物理机型号可登记，客户端与服务端配置分别保存。
- [ ] 同环境跨版本对比与跨硬件实验有明确标识，可比性原因可查。
- [ ] CLI 能非交互发起、查询、等待、取消、导出和比较。
- [ ] 提交/导入幂等，取消与服务恢复不留下未知的运行状态。
- [ ] UI 接入真实结果，并正确显示波动、缺失值和失败。
- [ ] 单 Job 可挂载现有 PVC 测试，结果不随 Pod 清理丢失。
- [ ] Agent 按 skill 完成执行与对比，并能恢复已有运行。
- [ ] 从零安装到结果对比的文档能由另一位使用者复现。

## 5. 验证安排与实施约束

每个阶段验证对应边界：解析和比较采用真实 fixture；任务管理验证进程与恢复；UI 验证真实 API；Kubernetes 验证挂载和持久化。通用 CI 只执行小规模功能测试，不用共享 CI 机器上的吞吐波动判定性能回退。

第一项编码任务固定为 **S0 + S1 的最小切片：一个顺序读模板 → plan → exec → fio 原始输出 → 规范化结果包**。该切片通过后再扩充写入、随机和混合负载，随后进入 S2。

进入真实性能与集群验收前，准备专用 Linux 测试路径、文件系统版本与环境资料、测试 namespace/PVC、独立结果存储和镜像分发方式。代码与 fixture 开发可先行；真实结果与集群支持声明以实际验收为准。

工作按 S0–S7 分批提交，每批提交说明对应能力、验证结果与已知限制。当前路线图不触发代码实现、性能测试、集群部署或远程发布。
